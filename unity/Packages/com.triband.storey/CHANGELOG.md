# Changelog

All notable changes to this package are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the package adheres to [Semantic Versioning](https://semver.org/) as Unity defines it (MAJOR = breaking public API or data format, MINOR = additions, PATCH = fixes). Data format version: see `StoreyVersion.DataFormat`.

## [Unreleased]

### Added
- **Storey Shader Warm-Up** (`StoreyShaderWarmUp`, *Add Component ▸ Storey*): the pipeline states the city draws with, made before it first draws them (docs/PERFORMANCE.md §7.9). A state met for the first time mid-game is compiled in that frame. On Metal that is a hitch of milliseconds to tens of them, and the steady variant doubles the states a city can need. In a development build with **Trace** on, the component records the states a run uses with Unity's `GraphicsStateCollection`. It saves them when the app goes to the background or quits (`Storey <platform> <API>.graphicsstate` in the persistent data folder), and sends them to the editor when one is connected. Added to **Collections**, the collection for the device's platform and graphics API (and quality level) is made a few states a frame from the start, or all at once behind a loading screen. Works with the API in `UnityEngine.Experimental.Rendering` (6000.0 to 6000.4) and `UnityEngine.Rendering` (6000.5 on).
- `Documentation~/quality-tiers.md`: the URP settings to put beside each quality tier (rendering path, the GPU Resident Drawer, shadows, SSAO, HDR, MSAA, resolution, SH, stripping, warm-up), as starting points for the device runs to confirm.
- Profiler markers for the occlusion's halves, the props and the play kit (docs/PERFORMANCE.md §10.5), named as Storey's other stages are: "Storey occlusion: view and buildings in the way" and "Storey occlusion: cutaway" inside "Storey occlusion: frame" (`OcclusionCore.FrameView` and `FrameCutaway`, which `Frame` calls in turn), and "Storey props: frame". Storey Diagnostics names them when the main thread stalls in one.
- **P99 Frame Ms** in the quality asset (`StoreyQualitySettings.p99FrameMs`): the frame time that 99 frames in a hundred must be under for the play kit's Storey Performance Run to pass a path, 20 ms on the primary tier and 40 ms on the minimum tier (docs/PERFORMANCE.md §14). `Play.PerformancePaths` finds where the run goes: a layout's longest straight street clear of every building, its tallest building, and a point on each storey that the walk model places in that storey. `Play.FrameSeries` gives a series' percentiles.

### Changed
- The default lighting evaluates the ambient probe where URP's SH Evaluation Mode says, per vertex on mobile under Auto, as URP's Lit does: the colour passes of Opaque, Massing and Glass declare `EVALUATE_SH_MIXED` and `EVALUATE_SH_VERTEX`, the vertex stage evaluates it (`SampleSHVertex`) and the lighting takes it through `SampleSHPixel` (docs/PERFORMANCE.md §7.3). Every face is flat, so the per-vertex value is the pixel's. It sampled the probe per pixel whatever the mode, tens of instructions on every lit pixel. `StoreySurface.vertexSH` carries it to a project's own lighting. The colour pass's normal, vertex colour and window-pane values go to the fragment stage as `half`: Apple's GPUs keep vertex outputs between the stages, and halves take half the space (§7.2). The Color Palette Lit sample's shaders include these files; their lighting uses no probe.
- The massing's pixels and every palette lookup do less (docs/PERFORMANCE.md §7.4). A massing pixel found each of its four colours (wall, trim, roof, glass) with a lookup of its own. Each lookup read two colour-row entries and a detail colour that a style's slot never uses, asked the atlas for its size, and divided by its width. Now the four come from two loads of the colour row: the four entries share its first `uint4`, the remap row is in its third (`StoreyStyleColors` in `StoreyPalette.hlsl`). The atlas's size is found once. Any lookup, the LOD0 and LOD1 vertices' too, splits the atlas index with a shift and a mask when the atlas's width is a power of two (Color Pipeline's 512) and divides only otherwise: an integer divide by a uniform takes hundreds of clocks on Apple's GPUs. A massing pixel makes 11 loads and no divide, where it made 21 loads, 4 size queries and 8 integer divides and modulos. The same colours. The Color Palette Lit sample's shaders include these files, so they get it too.
- An artist's window, door or facade detail makes no garbage where it is placed (docs/PERFORMANCE.md §8.1). Each placement made two arrays of the kind's points, and each part a map, two lists and their copies, walk-in glass two arrays more: about 21 MB a LOD0 or LOD1 build with a 100-vertex window on the test cities, where the generator's windows make 0.1–0.3 MB. Each part is now made ready once, when its kind is registered (`OpeningKinds.Register`, `DetailKinds.Register`) or when first placed if its arrays changed since, and each placement transforms it straight into the builder. A build with that window now allocates what one with the generator's windows does. The same meshes byte for byte. A part's triangle naming a point the mesh hasn't, or a partial triangle at its end, is now left out whole: it pointed at another part's vertex, or past the mesh.
- On iOS the build threads run at the utility quality-of-service class, below Unity's main and render threads (docs/PERFORMANCE.md §9.1). They asked .NET for below-normal priority, which IL2CPP ignores there, so they competed with the frame's threads for the cores. Each sets its own class before its first build (`Plugins/iOS/StoreyThreads.c`, `StoreyThreads.Utility`, `BuildThreads.Configure` and `Reconfigure`). Every site now shares one count of build threads, the most any site's settings ask for (`BuildThreads.SharedCount`), or `StoreyThreads.Override`: each site resized them to its own quality asset's count, so two sites with different assets resized them in turn every frame. Storey Diagnostics has two settings for a run that measures them, **Build Threads** (every site's count) and **Utility Threads**. Its record names the count, each thread's class before and after, and every ten seconds how long detail took to come, from a build's start to its last mesh up, and how many buildings waited for a thread. Its frame line, and the stats overlay, show the builds waiting for their upload (`upl`, `LodStats.uploading`), and the overlay's "Meshes uploaded this frame" counts meshes. `SiteRenderer.DetailTimes`.
- A building's detail goes up a mesh at a time, and the main thread no longer writes its vertices (docs/PERFORMANCE.md §3.2, §4.1). The upload wrote every vertex's colour row and wall id (`PackedMesh.Finish`) and then uploaded all of a build's meshes in one frame, LOD0's opaque parts, its glass and its rooms, checking the budget only after the building. Now the rows and the walls are found on the main thread, which owns the building table, the vertices are written on a build thread, and the meshes are uploaded one at a time within the budget, the rest in the next frames. The building shows its new LOD once the last mesh is up. The building the player is in, and those in the camera's way, take all theirs at once; then come the buildings in view, then those built ahead. The builds being made and those waiting for their upload together are at most twice the build threads, a forced building's aside: no new one starts meanwhile, so finished builds don't pile up when the budget can't keep up. A build whose building is let go, or no longer wanted before its first mesh is up, gives its walls and chunks back. **Build Budget Ms** is now per tier, 2 ms on the primary tier and 4 ms on the minimum tier, whose frames are 30 fps (it was 6 ms on both), counted per mesh: a frame takes one at least when any is ready. A layout loading over frames shares that budget. Headless, the 3,000-building test city then loads in 39 frames with two build threads at 60 fps, every cell shown after 0.70–0.72 s and no load frame past 3.3 ms (with 6 ms: 20 frames, 0.39–0.51 s, the 90th percentile 6.2–6.5 ms). At 30 fps on the minimum tier it loads in 24–25 frames and 0.86–1.05 s. `PackedMesh.Finished`; `MeshUpload.Upload` finishes only a mesh not yet finished.
- Less of a load on the main thread (docs/PERFORMANCE.md §3.2, §6.2). In Play mode, loading over frames, a layout's site index (its buildings' bounds and grid, the neighbouring districts' buildings along the edge) and its load plan are made on a build thread after the parse (`SiteRenderer.Prepare`, `LayoutLoad.Plan`; `StoreySite` waits for them as for the parse), where `Show` made them on the main thread: about 9–10 ms for the 3,000-building test city (headless). A cell's massings are packed on a build thread too, in Play mode with build threads, and uploaded within the build budget in a later frame; the cell shows the meshes it had meanwhile, and one whose members change meanwhile is merged again once its pack is in. The editor, and a load done at once, pack as before. `Site.BoundsOf` looks at the footprint and each setback's shape once, where it asked every storey for its outline (2.3 ms for 3,000 buildings, from 7.5), and a site keeps each building's (`Site.Bounds`).
- Meeting a building no longer makes its pieces on the main thread (docs/PERFORMANCE.md §10.2). The occlusion's first ray at a pitched-roof building made its whole roof to find its rise (up to 5.5 ms); the massing's build, on a build thread as the layout loads, now keeps each roof's rise (`Roofs.Rise`). The walk model's shapes are made ahead on build threads (`PlayWorld.Prepare`, `ShapesPrepared`, `Preparing`), for the buildings within 24 m of the player and the neighbours of the one they are in, which the Storey Occlusion asks for each frame: on the walk-in test city's walk none was made when a building was met, where each was made then (0.9–2.6 ms at the 95th percentile). Sink's footprints are made in a shared builder and given back (`SinkFootprint.Build`; 2.4 KB of garbage each, from 83 KB), and a site keeps 32 at most, the least recently shown going first. The walk model and the occlusion state are kept per site (a new one cost 3.9 ms and 1.7 MB for 3,007 buildings at every district crossing, crossing back too) and made on a build thread when a site shows a new layout: occlusion starts a frame or two after a load, and the districts next door have theirs made ahead. Leaving a district undoes what the occlusion wrote into its table (a building in the way there stayed sunk). Each occluder slot keeps one footprint object, whose mesh, layer and state are set only when they change (§10.3): under the GPU Resident Drawer a renderer given another mesh is registered again, and two footprints swapped objects every frame.
- In Play mode a building the view can't do without (in the camera's way, the one the player is in) no longer holds the frame for its LOD0 (docs/PERFORMANCE.md §3.1). The renderer waited for its build, or made it on the main thread, before the frame went on: 75–135 ms for the largest towers on a desktop, about three times that on a phone, at a spawn, a teleport, or whenever a building came into the way without its LOD0. It now shows what it has (its shell, or its massing) until a build thread has its LOD0, which goes ahead of every other build and is uploaded whatever the budget; one already waiting in the queue is moved up. In the editor, and with no build threads, it is built at once as before. The build threads take builds by lane (`BuildLane`; `BuildThreads.Run`'s `lane`, `Promote`, `QueuedIn`): forced detail, then detail (the buildings in view first), then a layout's cells, then parses and prefetch. LOD0 is built ahead too (`SiteRenderer.Prefetch`, `LodManager.Update`'s `prefetch`) for the buildings along the camera's line to the player and round the player, and round a point asked for (`StoreySite.PrefetchAround`, which the play kit's character asks at every spawn): after the forced and those in view, kept past the residency cap while asked for. `StoreySite.DetailReadyAround` says when every building round a point has its LOD0, for a spawn or teleport behind a fade or a loading screen to wait for. `SiteRenderer.HasDetail` and `BuildingsNear`; `LodManager.Frame.Forced`, `Seen` and `Prefetched`.
- Nothing is open from outside any more, so back faces can be culled (docs/PERFORMANCE.md §7.1). The prototype draws every face two-sided, and where a surface is one-sided, or a gap is left, from outside its back shows; culled, a hole would. Unity now draws a back or a closing face there, by Unity only (`MeshBuilder.Backing` and `BackingTris`, `Lod2Mesh.BackingTris`; the prototype's census leaves them out), a centimetre or so off, since a cut or fading building's materials draw both sides and two faces back to back would flicker: each roof part's back, LOD2's too (`Dim.BACK`, 1.3 cm); under a pitched roof or a terrace's, the walls' tops (LOD0, LOD1) and a lid (LOD2); a slab's edge above a curtain wall's opening; the backs of bands, plinths and foundations across an opening; a core wall's end against the building's wall, behind its windows; a flight's landing and an escape's platform where they meet the wall; the parapet over a core flush with the wall at LOD1, whose bulkhead stands clear of it; the slit a corner cut leaves above a lower neighbour (LOD2); the sill tops and lintel undersides round a core's door. On the 1,000-building walk-in test city they are 1.3 % of LOD0's shell, 0.3 % of LOD1 and 9 % of LOD2 (4,265 triangles in all). The slabs' edges and the strips' backs, which only clear glass shows, go with LOD0's rooms (23 % of the rooms' triangles), drawn only near; LOD1, whose windows are opaque, has none. `BackFaceTests` casts 4,000 rays from eyes round each building of the demo street, the variants and a 40-building walk-in city, at every LOD as it is drawn (LOD0 near, its rooms in and its glass clear, and far, its rooms out and its panes painted over), and finds no back face first, slivers aside: a ray within 6° of the face, or a front face within 5 cm or up to 30 cm behind.
- LOD0's rooms are drawn apart from the rest (docs/PERFORMANCE.md §7.7): the inner faces of a storey's outside walls, its partitions and its cores, which only its windows show. The generator marks them (`MeshBuilder.Inside`, `InsideTris`), the packer puts them in meshes of their own (`MeshPack.Pack`'s `rooms`), and the site gives them renderers of their own, named "LOD0 rooms". They draw with the LOD0 while its nearest point is within the distance LOD0's windows are painted over from (the LOD0 distance; on from 5% beyond it, off from 10%), or while the building can show its inside: cut, fading, isolated against, the player's, kept at full detail. They cast shadows only for the building the player is in, whose indoor light needs them. Floors and ceilings stay with the shell, which casts, so the sun still reaches a storey only through its own windows. Whatever an opening shows at any distance stays with the shell too: a storey with a doorway with nothing in it (`MeshBuilder.SeeThrough`; a glazed door's glass is painted over as a window's is) or an artist's glass, which isn't painted over; the top storey under a roof bulkhead's door; every storey under an atrium's skylight or a straight flight's railed roof opening. The rooms are 18.6% of a LOD0's triangles on the walk-in test city and 21.9% on the demo street (headless). In the two views recorded on an iPhone 11 Pro every LOD0 is within the painted-over distance, so the colour pass draws what it did, and the shadow casters lose 17.4–17.6% of LOD0's triangles. An orthographic camera (`SiteRenderer.LodEye.orthographic`), the fixed LOD and **Windows Clear At** 1 draw them always. `LodStats.roomsShown`; Storey Diagnostics' frame line shows the LOD0s drawing their rooms (`rooms n/m`) and how many switched.
- The automatic LOD asks for detail in view first: the forced buildings, then those in the camera's view by pixels per metre, then the rest. A building out of view gets no LOD0 built and shows its shell until it comes into view (docs/PERFORMANCE.md §9.2). `LodView` (a perspective camera's planes in site space), `LodManager.Update`'s view; `SiteRenderer.LodEye` carries the camera's forward, up, field of view and aspect.
- A building shown at LOD1 casts its shadow through its massing in the cell, which has its outline and heights in about 43 triangles against LOD1's 980 (docs/PERFORMANCE.md §7.8). LOD1's renderers cast none (`ShadowCastingMode.Off`), and a cell whose buildings show LOD1 but none LOD2 draws `ShadowsOnly`. The massing's shadow caster treats LOD1 and LOD2 alike; LOD0 keeps its own shadow.
- The opaque and massing shaders queue at AlphaTest, and the steady copies of their materials at Geometry, so every opaque draw comes before every discarding one, as Apple's GPUs want (docs/PERFORMANCE.md §7.6). The Color Palette Lit sample's shaders too: re-import it to get them.
- Each pass and variant hands its fragment stage only what it reads (`Varyings` in `StoreyLit.hlsl`, `StoreyUnpack`): a tile-based GPU writes every vertex output to memory between the two stages (docs/PERFORMANCE.md §7.2). The steady depth and shadow passes output the position alone (4 floats, from 34 on Opaque and 42 on Massing) and the others the position and five values (9); the steady colour pass leaves out the cutaway's and the occluders' values (24 floats on both, from 34 and 42); the massing carries no vertex colour or pane, and only the non-steady colour pass reads `_StoreyWallData`.
- A placed detail's kind is its id (`DetailData.kind`, a string): "ac", "vent", "dish", "escape" or "awning", as layouts store it, or a Facade Detail asset's. `DetailKind` is now a registered kind, a class, where it was an enum of the five; `Details.Catalogue`, `Details.Spec` and `Details.Item.spec` are gone (`DetailKinds.Get`, `Details.Item.kind`). `Facades.DetailAt` and `ToggleDetail` take the kind's id; `Details.EscapeRun` takes how much flush wall the kind needs each side. Layouts read and write as before. A layout naming a detail kind the project doesn't have now loads, keeping the detail unbuilt; it failed to load before.
- A building's LOD0 and LOD1 renderers are switched off while that LOD is neither shown nor fading out, and on again when it is (`SiteRenderer`). The meshes kept for later under the residency caps were drawn every frame, their every vertex fetched and clipped in the vertex shader, in every pass that draws them. On the five-minute walk of the 3,000-building test city (headless), that was 30% of the detail vertices held: 0.51 million a frame on average and at most 1.07 million, before frustum culling (35% on the minimum tier, 22% in the walk-in city).
- **Build Budget Ms** is a frame's, for every site together: each site had all of it, so districts loading at once spent it several times over in one frame. Each site still builds one when any is wanted. In edit mode each site keeps its own.
- A site keeps at most 64 colliders (**Colliders Kept** in the quality asset, `LodSettings.MaxColliders`; 0 keeps them all). A building's collider comes with its LOD0 and stays when the LOD0 goes, and they piled up for the session: past the cap, those whose LOD0 went longest ago lose theirs now (`LodManager.OldestDetail`), made again with their next LOD0; one showing its LOD0 always keeps it. Headless, a 30-minute walk through the walk-in test city kept 125 colliders (1.4 MB of meshes, besides PhysX's cooked copies, which aren't measured) and keeps 64 now (0.6 MB), with the same LOD0 builds.
- Massings reuse their memory. A massing is given back once its cell is packed (or it is uploaded, with the fixed LOD) and the next one built takes it, its lists keeping their room (`Lod2Mesh.Make`, `Recycle`, `ForgetSpares`; 32 kept); and a massing's quads are made without arrays. The same massings byte for byte. A massing allocates 24 KB on the 3,000-building test city (was 62) and 16 KB on the walk-in one (was 55); loading the 3,000-building city allocates 135–151 MB (was 318–328 before this and the cell packing below, the layout's parse not counted), measured headless.
- A cell's massings are packed straight into the upload's layout (`Cells.Pack`, `Cells.HalfVertex` and `Cells.FullVertex`, `MeshUpload.Upload(Cells.Packed, …)`), in chunks that go back once the cell is uploaded, where they were merged into lists (`Cells.Merge`, still there) and copied into new arrays for the upload. The same vertices. Loading the 3,000-building test city, the main thread made 78 MB of garbage merging cells and 10 MB more for the upload arrays; it now makes none, and works a third as long on the load with the iPhone 7 setting (83–120 ms, was 286–340, headless). A single building's massing (the fixed LOD) is packed the same way. `MeshUpload.MassVertex` and `MassVertexHalf` are gone.
- In Play mode, loading over frames, a site's layout and its neighbours' are parsed on a build thread (`StoreyDocumentAsset.DocumentOffMainThread`, `Lod.LayoutParse`), and the site is shown the frame they are ready. The parse held the frame a site started in, 0.1–0.2 s and 60 MB of garbage for the 3,000-building test city (measured headless), so a district streamed in made a hitch. The site is `Loading` meanwhile, and its `PlanArea` is null until its layout is parsed (asking for it no longer parses it). Edit mode, and Play mode with **Load Over Frames** off, parse at once as before. `StoreyDocumentAsset.Parsed` gives the layout only if it is parsed already.
- A layout loads in a fifth of the frames with two build threads (21–27, was 127–132) and a third with three (20–25, was 63–71). Its cells' massings are built four a build thread ahead of the cell taken (`LayoutLoad.AheadPerThread`), where one a thread left the threads idle most of the load: each frame took only the few cells that were ready. Measured headless on the 3,000-building test city, with the cell packing and the massings' reuse above, every cell shows after 0.71–0.73 s with two build threads at 60 fps (was 2.4–2.5 s) and 0.96–1.06 s at 30 fps on the minimum tier (was 4.5–4.6 s); the first view's detail is done after 1.36–1.47 s and 1.33–1.36 s (was 2.4–2.5 and 4.5–4.6 s). A load's frames now spend up to the build budget on it (**Build Budget Ms**), where they spent 1–3 ms. The massings in flight hold no measurable memory more. `LayoutLoad.InFlight` counts them.
- Storey keeps no state per thread. Unity's manual warns that the .NET `[ThreadStatic]` attribute crashes a Unity script, and the build threads' spare mesh builders, wall-panel and weld lists, triangulator nodes and mesh packer were thread-static, as were the walk model's query lists. A mesh builder now keeps its own panel and weld lists (one thread uses it at a time) and its spares are shared by every thread (16 kept, where each thread kept 6); the triangulator's arrays and nodes (`TriScratch`, an `Earcut` instance), a mesh's packer and the walk model's query lists are lent for each call and given back, a lock each way. `Earcut` is a class whose instance `Tessellate` reuses its nodes; the static one makes an instance. The same meshes, the same 91 MB of garbage on the five-minute walk and the same build times; Storey holds 0.1 MB more after the walk. `PackageLayoutTests` fails if package code declares a `[ThreadStatic]` or `[ContextStatic]` field or uses `ThreadLocal<T>`.
- Detail builds make almost no garbage of their own. The wall panels, their triangulation (Earcut) and the openings they merge use their builder's own lists, nodes and copies again for every wall (`Triangulate.Shape`'s list overload, `TriScratch`, `Earcut`'s instance `Tessellate`, `Opening.Set`); each wall's openings and panel options are made again wall after wall (`Facade.Ops`' list overload with an `OpeningPool`, `Facade.PanelOpt.Set`); four-cornered polygons are drawn without an array (`MeshBuilder.Quad`); and the details' hash no longer boxes its numbers (`Details.Hash01`'s typed overload). The same meshes. The party-wall memo is keyed by numbers instead of text, and the details work out a storey's corners once instead of once an edge. With the chunks above, the five-minute walk of the 3,000-building city makes 91 MB of garbage instead of 2,818, a sixth of it the chunks' first fill (32 MB in its busiest second, the first builds, instead of 376; 0.3 MB in a typical busy second), holding 16.6 MB for it; a building's detail build takes 15–18% less time on a worker, and its LOD0 alone allocates 1.8–2.6 MB instead of 13–18 on the test cities.
- Buildings that nothing can hide draw without discard. The opaque and massing shaders have a steady variant (`#pragma multi_compile_local _ STOREY_STEADY` in every pass: no discard, no Sink), and the renderer switches each building's opaque and massing renderers, and each cell's, to a copy of the material with it on while the building isn't cross-fading, isolated against, in the way, or the player's (or carrying a party wall with it): `Occlusion.Steady` holds the rule, `PackedMesh.Mates` the party-wall neighbours, `StoreyGlobals.ActiveIndex`, `IsolateAmount` and `IsolatedIndex` the view. Apple's GPUs can then hide most of the city's pixels before shading them; how much that saves needs Xcode's GPU counters on a device. A project shader without the variant keeps one material and draws as before. `StoreyQualitySettings.occlusionOnFarMaterials`, which did nothing, now keeps massings in the way steady when off (`LodSettings.FarOcclusion`).
- Colliders are cooked without holding a frame: a batch is scheduled on Unity's job workers (`Physics.BakeMesh` in an `IJobParallelFor`) and its colliders are assigned in a later frame, once it has finished, where the main thread used to wait for the whole batch in the frame that started it. A building released or rebuilt meanwhile has its collision mesh destroyed only after the batch; edit mode still finishes the batch at once.
- Detail and massing builds run on Storey's own build threads (`BuildThreads`, a `TaskScheduler`) instead of the .NET thread pool: long-lived background threads named "Storey build N", below normal priority where the platform allows it, and registered with Unity's Profiler, where `Storey.Generate LOD0`, `Storey.Generate LOD1`, `Storey.Pack` and `Storey.Collision mesh` markers show their work. How many is `StoreyQualitySettings`' new **Build Threads**; automatic (0) is two on a phone or tablet and one fewer than the cores, at most four, on a desktop, where it was one fewer than the cores everywhere, as many as Unity's own job workers. The threads end when the player quits and before the editor reloads scripts. `StoreyTimings`' stages are `ProfilerMarker`s.
- Detail builds reuse their memory. A mesh builder's lists and a packed mesh are made of fixed-size chunks (`Chunks`, `ChunkList<T>`: 2,048 elements): a list grows a chunk at a time without copying, and gives its chunks back when its builder is recycled (`MeshBuilder.Make` and `Recycle`) or its mesh uploaded (`PackedMesh.Release`), and any chunk fits the next build whatever the sizes of the two buildings. A mesh past 65,535 vertices is split into parts without a whole-mesh copy. The same meshes byte for byte. The chunks kept between builds are capped by `StoreyQualitySettings`' new **Mesh Chunks Kept MB** (16; 12 on the minimum tier), each type of chunk to its share of what builds take, so a builder's lists, given back first, can't fill the cap and leave its packed mesh's none. A builder holds a vertex's normal and colour as indices into its own tables of them (`IndexedList`, `MeshBuilder.N` and `C`: 4 bytes each instead of 24), so its lists take 46 bytes a vertex instead of 86, and the largest builds need a third fewer chunks. `MeshBuilder`'s lists and `PackedMesh.V`, `Cut` and `I16` are `ChunkList`s, uploaded a chunk at a time; `Site` no longer records each building's last size.
- LOD0 and its glass are packed without welding (`MeshPack.Pack`'s `weld`): the generator shares their vertices already, and welding found 0.27% more on the test cities while taking a fifth to a quarter of a worker's build. A LOD0 build takes 20% less worker time on the 3,000-building test city (6.6 ms, was 8.2) and 27% less on the walk-in one (12.2 ms, was 16.6). LOD1 is still welded (3.7% fewer vertices). `WeldTests` fails if the generator starts making duplicates.
- The building table uploads only the chunks that changed each frame (`DirtyChunks`): on the five-minute walk of the 3,000-building test city, 1.0 KB a frame on average where the whole wall, state and occluder buffers went up every frame (344 KB). `BuildingTable.SetState`, `SetWall`, `SetWallData` and `MarkOccDirty(slot)`; writing straight into the arrays still works with the `Mark…Dirty()` calls, which upload the whole buffer. The wall tables start at 8,192 wall ids and double when full, up to 65,536 (`WallIdsStart`): 2.2 MB less in all.
- The automatic LOD passes over squares of buildings that can't change: it keeps them in 128 m squares, and a square whose buildings all show their massing (or nothing), with neither its nearest nor its farthest point crossing a threshold, is skipped whole. The picks are exactly those of looking at every building (`LodSquaresTests`); on the 3,000-building test city a frame takes 46 µs, not 157 (Release). Ties in the build and drop lists now go in building order. The caps look only at the buildings holding meshes.
- The far city's cells store each massing's facade numbers (metres along a wall and up a run, the window span, the bay's width, the kind) as 16-bit floats: 36 bytes a vertex instead of 48, 9.8 MB of GPU memory instead of 12.8 on the 3,000-building test city. The shader reads them as it did; they are 2.5 cm off at most on the test cities, a tenth of a pixel where a massing shows. A GPU that can't read 16-bit floats in a vertex (`SystemInfo.SupportsVertexAttributeFormat`) gets the 48-byte vertex. `Cells.HalfVertex`, `MeshPack.Half`.
- A layout's massings are built on the worker threads, a few cells ahead of the main thread, which meanwhile writes and merges the cells before: on the 3,000-building test city the main thread works about 50 ms of the load instead of about 300 ms (headless, 3 workers). `LayoutLoad`.
- A building's collision mesh is made on the worker thread with its first LOD0, not on the main thread (0.4 ms a building on average on the test city, 1.9 ms in the walk-in one).
- A building built again (its LOD0 or LOD1 dropped and wanted back) is made at the size of its last build, without growing its lists: LOD0 and LOD1 together allocate 4.8 MB, not 8.7 (10.5, not 18, in the walk-in city). `MeshBuilder`'s `vertices` and `indices`.
- Detail meshes are packed into the upload's vertex format on the worker thread that built them (`MeshPack`, `PackedMesh`). The main thread only fills in each vertex's colour row and wall id and copies: 0.13 ms a building on the 3,000-building test city, was 2.5 ms (worst 42). A finished build waits for its upload at 0.8 MB, not 3.0 (1.7, not 6.5, for a walk-in building). `MeshUpload.Upload(PackedMesh, …)`; `MeshUpload.Vertex` and `Cutaway` are now `PackedMesh.Vertex` and `Cutaway`.
- A LOD0 mesh past 65,535 vertices comes in parts with 16-bit indices, not as one mesh with 32-bit ones. The test city's 16 largest LOD0s take 8% less GPU memory (90.5 MB, was 98.6), in 51 meshes instead of 32.
- Building and welding a LOD0 allocates half as much: 14 MB instead of 29 for a building of the walk-in test city, on average. `MeshBuilder.W`, a copy of each vertex's wall data that nothing read since the walls' data moved into the building table, is gone; `MeshBuilder.Weld` works in place with a table of vertex indices instead of a dictionary of copied keys; boxes add their faces with `MeshBuilder.Quad`, without an array each. The meshes are the same to the bit.
- What is kept of a building's LOD0 after upload is its shape (`Lod0Shape`: the collision segments and the wall list), not the generator's whole result. `SiteRenderer.ShapeOf` and `StoreySite.BuiltShape` replace `Lod0Of` and `BuiltLod0`; `CollisionMesh.Build` takes a shape; `Lod0Result.Shape`. The walk model's `ShapeOf`, `Use`, `ShapeCount` and `ShapesBuilt` replace `Lod0Of`, `UseLod0` and `Lod0Count` (docs/CITY.md §7).
- LOD1's walls are flat: a plain window is an opaque pane 3 cm proud of the wall (`Lod1.PaneProud`), its reveal shaded in the shader at the pane's sides and head (`StoreyRevealShade`), instead of a hole cut in the wall with modelled reveals. Doors and artist-made windows keep their openings. On the 3,000-building test city LOD1 goes from about 4,230 triangles a building to 980. `Lod1.Build(..., recessed: true)` builds the prototype's LOD1 for the parity tests.
- Every object a Storey Site makes (buildings, their LOD objects and colliders, the merged cells, Sink's footprints) is on the site's own layer, not Default; changing the site's layer moves them. `SiteRenderer.Layer`.
- `StoreyQualitySettings`' level-of-detail fields are now the automatic LOD's numbers (`lod0PixelsPerMetre`, `lod1PixelsPerMetre`, `lod2PixelsPerMetre`, `hysteresis`, `fadeSeconds`, `farDistance`, `lod0Residency`, `lod1Residency`, `buildBudgetMs`), with defaults from the prototype. `ToLodSettings`, `ApplyTo`.
- Cut corners are kept as one corner: `CornerData` (the building's and a setback's `corners`), and `CornerCuts` (`Sharp`, `Around`, `Cut`, `Clear`, `CutAll`, `ClearAll`). The outline still holds the cut's points. `CornerShape` moved to the `Triband.Storey` namespace.
- LOD0 vertices are 16 bytes smaller (32 bytes now, with the building tag). They carry only the cutaway kind and wall id; each wall's start and normal sit once in the building table (`_StoreyWallData`), and the shader reads them by id. On the demo street LOD0 goes from 4.6 to 3.1 MB.
- `MeshUpload.Upload` welds exact duplicate vertices (`MeshBuilder.Weld`, about 1% of LOD0's; every triangle is unchanged), and calls `Mesh.Optimize` when asked. `SiteRenderer` asks in Play mode, not for the editor's previews.
- `StoreyGlobals.SetOcclusion` takes the player's chest (world space) and the hole radius in metres. The shader projects the player itself, so Cutout and Fade hold on reversed-depth platforms and flipped render targets.
- A building's row in the building table is its index in the layout, so party walls find their neighbour in the shader.
